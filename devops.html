DevOps: from release night to a change that ships itself

Writing software is half the job. The other half is getting each change to customers safely: building it, checking it, packaging it, putting it on servers, and noticing when it misbehaves. Teams used to do that by hand, once a month, late at night, with a long checklist and crossed fingers. DevOps is the habit of doing it in small steps, many times a day, with a machine doing the repetitive parts and the same people owning the code and how it behaves once it is live. This lab starts on release night, builds the path one part at a time, and explains what infrastructure as code is. It needs no background: if you have ever followed a recipe, you can run it.

Neighbours. Where the servers live, networks and load balancers included, is the cloud lab. Running the packaged app across many machines is the Kubernetes lab, which picks up at version 1.4 of the shop, where this lab leaves off.

Release night, then a change that ships itself

In plain English: a team of three looks after a small online shop. Once a month they hold release night: forty changes bundled together, fourteen steps done by hand from a checklist, three hours after midnight, and something breaks. Then the hunt starts: which of the forty did it? DevOps replaces that night with a path every change travels alone, minutes after it is written. A machine builds it, tests it, packages it and puts it on the servers, and the team watches how it behaves. Nothing about the software got cleverer. The changes got smaller and the path got automatic.
The picture for the whole lab. A bakery chain. The recipe book, with every change to every recipe written down, is the code and its history. The test kitchen bakes and tastes every changed recipe before it goes anywhere. A loaf that passes is boxed, numbered and put on the storeroom shelf. The van takes that same box to the branches, one branch first if the recipe is new. Every branch is built from the same floor plan, so a loaf that bakes well in one bakes well in all. And somebody reads the complaints book every morning. Dev is the bakers, ops is the people who run the shops, and DevOps is the two working as one team.

Three abbreviations
CI, continuous integration: everyone’s changes are merged into the main copy every day, and a machine builds and tests each one.
CD, continuous delivery: every change that passes is packaged and ready to release at the press of a button. Continuous deployment goes one step further and removes the button.
IaC, infrastructure as code: the servers come from a file.
Why “Dev” and “Ops”
Developers were paid to change things. Operations were paid to keep things stable. Each change was thrown over a wall between them, and each side blamed the other when it broke. The fix was not a tool. It was one team that owns the change from the keyboard to the customer, with the tools on this page taking the drudgery out of the middle.

Build and test: every change is checked within minutes of being saved

In plain English: continuous integration, CI for short, is two habits. First, everyone merges small changes into the main copy of the code every day, instead of working apart for weeks and colliding at the end. Second, a machine reacts to every saved change. It fetches the code onto a clean computer, builds it, runs the tests and reports back in minutes. A change that fails goes no further, and the person who wrote it hears while they still remember writing it.
Why the clean machine matters. A laptop collects years of installed tools and half-finished experiments. Software that builds there may build nowhere else. The pipeline starts from an empty machine every time, so if it builds there, it builds.
The pipeline file, the part that matterson: push jobs: test: steps: - checkout - run: npm ci # install the libraries - run: npm test # run the tests package: needs: test steps: - run: docker build -t shop:$VERSION . - run: docker push registry.example/shop:$VERSION secrets: REGISTRY_TOKEN deploy: needs: package environment: production # a person approves steps: - run: ./deploy.sh shop:$VERSIONsimplified: every pipeline tool spells these six ideas its own way
The six ideas in that file
on says what starts the pipeline. A job is a group of steps on one clean machine. A step is one command. needs says which job must pass first. secrets hands over a password without writing it in the file. environment names where it deploys, and who must approve.

Three kinds of test. A unit test checks one small piece of code in a fraction of a second. An integration test checks that two or three pieces work together, in a second or two. An end-to-end test drives the whole system the way a customer would and takes half a minute. You want many of the first, some of the second and a few of the third.

Publish: one package, a rehearsal, then customers

In plain English: the pipeline has produced a package: version 1.4 of the shop, sealed and sitting on the registry shelf. Publishing is everything after that. The rule that matters most is build once. The package that passed the tests is the one that goes to the rehearsal copy and then to customers, unchanged. Only the settings differ between places, such as which database to talk to. Rebuild for production and you are shipping something nobody tested.
Delivery and deployment. With continuous delivery, every change that passes is ready to go and a person presses the button. With continuous deployment there is no button: passing the checks is the approval. Both need the same thing underneath, a way to put a version in front of customers that does not hurt much when the version is bad. There are four common ways, and they trade speed, cost and risk.
WayWhat happensGood forThe catch
All at onceEvery server is stopped, swapped and started together.A tiny site whose visitors forgive a blink.A minute of error pages, and a bad version reaches everyone.
RollingServers are swapped a few at a time. Each new one is checked before it takes customers.The everyday default.A bad version that passes its checks spreads until someone notices.
Blue-greenA second full set is started beside the old one and checked. Then the front door is switched over in one move.Releases that must be undone in seconds.You pay for double the servers while both sets run.
CanaryOne server gets the new version and a few customers in a hundred. Its numbers are compared with the rest before anyone else gets it.Risky changes and large audiences.Slower, and it needs good monitoring to compare the two groups.
Environments, the usual three
Test is where the pipeline tries the package first. Staging is the dress rehearsal: built like production, used by nobody outside the team. Production is the real one. A package moves forward only when it has passed in the place before.
Deploying is not releasing
A feature flag is an on-off switch inside the software. The new checkout can be deployed switched off, turned on for the team, then for a few customers in a hundred, then for everyone. Turning it off again takes seconds and needs no deployment at all. Deploying moves code. Releasing lets customers see it.

Infrastructure as code: the servers come from a file

In plain English: infrastructure is everything the software runs on: the servers, the networks between them, the databases, the front door that shares out customers, the permissions. For years it was built by clicking through a cloud provider’s web pages, one box at a time. That works once. Six months later nobody remembers what was clicked, the rehearsal copy is “nearly the same” as the real one, and rebuilding after a disaster takes days of guessing. Infrastructure as code, IaC for short, means writing what you want in a file: three web servers this size, one database with backups, one front door. A tool reads the file, compares it with what really exists, and makes the changes.
Why a file changes everything. A file can be kept in the repository beside the code, so every change to the servers has an author, a reason and a review. The same file can build the rehearsal copy and the real thing, so they truly match. It can be run again after a disaster. And it can be read: the file is the documentation, and it cannot go out of date, because it is what built the thing.

The loop you actually run
Write the change in the file.
Plan: the tool compares the file with the real world and lists exactly what it would add, change or destroy. It touches nothing.
Review: a colleague reads the plan the way they would read a change to the code.
Apply: the tool makes the changes and notes what it built in its state, its own record of what exists.

Run it and watch it: the half that makes it a loop

In plain English: shipping is not the end. The moment a version is live, the question becomes: is it behaving? Monitoring answers with three kinds of evidence. Metrics are numbers measured every few seconds: how many requests, how many failed, how long they took. Logs are the software’s diary: one line for each thing that happened. Traces follow one customer’s request through every part of the system it touched, with the time spent in each. An alert is a rule on a metric that phones somebody when a line is crossed.
When it breaks. Put the last good version back first and investigate second: the pipeline made that a two-minute job on purpose. Afterwards the team writes down what happened and what would have caught it sooner, without hunting for someone to blame. People who are punished for mistakes hide them, and hidden mistakes are the expensive kind. What the team learns becomes the next small change, which is why DevOps is drawn as a loop and not a line.
The four numbers
Research across thousands of teams settled on four measures, often called the DORA metrics after the group that studied them. How often you ship, the deployment frequency. How long a change takes from saved to live, the lead time. How often a release goes wrong, the change failure rate. How long recovery takes when one does, the time to restore. The first two measure speed and the last two measure stability. The finding that surprised people is that good teams are better at all four at once.
You build it, you run it
The team that writes the software also carries the phone for it. That sounds like a punishment and works as a design rule: people who are woken by their own software write software that does not wake people. It only works with the rest of this page in place: small changes, a fast way back, and numbers everyone can see.

When someone asks… the short answer

In plain English: each line is a question as a colleague, a client or a panel would put it, then the answer that shows you have done it.
“What is DevOps, in one sentence?” → A way of working where the people who build software and the people who run it are one team, changes are small, and a machine does the path from saved change to live. It is not a tool or a job title; the tools only make the habit cheap.
“What is the difference between CI and CD?” → CI, continuous integration, merges everyone’s small changes daily and has a machine build and test each one. CD, continuous delivery, takes what passed and makes it ready to release at the press of a button; continuous deployment removes the button.
“Why release more often? Surely that is riskier.” → The number of bugs is the same either way. Small releases make each bug cheap: one suspect, found in minutes, undone alone. A monthly bundle of forty changes is nearly certain to contain a bug, with forty suspects.
“What is a pipeline?” → The automatic path a change travels once it is saved: check, build, test, scan, package, deploy. It stops at the first failure and tells the author within minutes.
“Why build once?” → The package that passed the tests must be the one customers get. Rebuild for production and you ship something nobody tested. Only the settings should differ between places.
“What is an artifact, and where does it live?” → The sealed, numbered result of a build, usually a container image. It lives in a registry, a shelf any server can fetch from by version, which is also what makes putting an old version back possible.
“What is infrastructure as code?” → Describing servers, networks and databases in files kept with the code, so a tool builds them the same way every time. It gives you review, history, true copies of production and a rebuild after a disaster.
“Declarative or imperative?” → Declarative says what should exist and the tool works out the steps, so running it twice changes nothing. Imperative is a list of steps that assumes where you start. Infrastructure as code tools are declarative.
“What does plan do before apply?” → It compares the file with the real system and lists every addition, change and destruction without touching anything. Reading it is how you catch a rename that would delete a database.
“What is drift, and what do you do about it?” → The real system no longer matches the file because someone changed it by hand. The next plan shows it. Then you either apply, which puts the file back in charge, or write the change into the file if it was right.
“Rolling, blue-green or canary?” → Rolling swaps servers a few at a time and is the everyday default. Blue-green runs a second full set and switches in one move: an instant way back at double the cost. Canary gives a few customers the new version first and compares the numbers.
“A release just broke production. What first?” → Put the last good version back, then investigate. Going back takes two minutes because the old package is still on the shelf; the investigation can take as long as it needs once customers are safe.
“How do you know whether the team is doing well?” → Four numbers: how often you ship, how long a change takes to go live, how often a release goes wrong, and how long recovery takes. Speed and stability improve together when changes are small.
“Where do passwords go?” → In a secrets store, handed to the software when it runs. Never in the code or the pipeline file: the repository keeps everything for good, so a pasted password must be changed, not just deleted.
“Deploy or release?” → Deploying moves code onto servers; releasing lets customers see it. A feature flag separates the two: ship the code switched off, turn it on for a few people, and turn it off in seconds with no deployment.
Words in these lines. Repository: the shared store of the code and its whole history. Pipeline: the automatic path from a saved change to running software. Package, or artifact: the sealed, numbered result of a build. Container image: the usual kind of package today, an app boxed with everything it needs. Registry: the shelf packages are kept on. Staging: the rehearsal copy. Production: the real one. Plan and apply: the dry run and the real run of an infrastructure tool. Drift: the real system no longer matching the file. Feature flag: an on-off switch inside the software. Secrets store: the locked place passwords live.
