Kubernetes: from one Docker server to a fleet that runs itself

A container is your app packed in a box with everything it needs. Docker runs that box on one computer. Kubernetes runs hundreds of boxes across many computers and keeps them running: it restarts the ones that die, adds more when the queue grows, swaps in a new version without anyone noticing, and finds a new home for everything when a computer fails. This lab starts with one server at 2am, builds the cluster up one part at a time, deploys a real app through it, and is honest about when you do not need any of it.

Neighbours. The network a cluster lives in, VPCs, subnets and load balancers, is built from nothing in the cloud lab. The three clouds each sell a managed Kubernetes, which the atlas lines up. Serving a model on a cluster is the fleet lab.

One server at 2am, then a fleet that looks after itself

In plain English: with one Docker server, your app runs in a box on one computer. If the box crashes, someone restarts it. If the computer fails, the site is down until someone builds another. If Monday brings ten times the traffic, someone adds boxes by hand. Kubernetes is the manager that does all of that for you: you tell it “keep three copies of this box running” and it keeps three running, on whichever computers have room, whatever happens.
The analogy for the whole lab. Docker is a shipping container: standard box, fits any ship, any crane. Kubernetes is the port. The port does not care what is in the boxes; it decides which ship each box goes on, moves boxes off a ship that is sinking, and brings in more ships when the queue of boxes grows. You still pack the boxes.

The box: what a container actually is

In plain English: “it works on my machine” is the oldest excuse in software. A container ends it. You write a short recipe, a Dockerfile, that says which base to start from, which files to copy in, what to install and what command to run. Docker bakes that into an image: a frozen, complete copy of your app and everything it needs. Anyone who runs the image gets exactly your app, on their laptop, on a server, in a cluster. A running image is a container.
Not a virtual machine. A virtual machine is a whole pretend computer with its own operating system: gigabytes, minutes to start. A container shares the computer’s operating system and only packs your app and its libraries, the ready-made code it builds on: megabytes, a second to start. That is why you can run fifty containers where you could run five virtual machines, and why a cluster can start and stop them all day.
The recipeFROM python:3.12-slim COPY . /app RUN pip install -r /app/requirements.txt EXPOSE 8080 CMD ["python", "/app/server.py"]five lines: start from, copy in, install, which door, what to run
The three words
An image is the baked, unchanging copy. A container is that image running. A registry is the shelf images are pushed to and pulled from, so a cluster on the other side of the world can fetch exactly the one you built.

Deploying an app: say what you want, not what to do

In plain English: with a plain server you tell it what to do, step by step: copy the files, start the process, start it again. With Kubernetes you write down what you want, in a file: this image, three copies, replace them one at a time, send traffic to door 8080. You hand the file over with one command, and from then on the cluster keeps the world matching the file. Change the file, apply it again, and the cluster works out the steps. That one idea is why a deployment that took an afternoon of typing becomes a change to a line.
The file, the part that matterskind: Deployment metadata: name: shop spec: replicas: 3 template: spec: containers: - name: shop image: registry.example/shop:1.4 ports: - containerPort: 8080three copies of image 1.4, listening on 8080; change 3 to 9 to scale, 1.4 to 1.5 to update
The four commands you actually run
All four go through kubectl, the command-line tool you talk to the cluster with.
kubectl apply -f shop.yaml hands the file over.
kubectl get pods shows what is running and its state.
kubectl logs shop-7d9f-x2k reads one pod’s output.
kubectl rollout undo deployment/shop puts the last version back.
everything else is a variation on these four

When a cluster earns its keep, and when it does not

In plain English: Kubernetes is a port. A port is the right answer for a shipping company and the wrong answer for one person with one van. Between the two sits a third option most people skip: a managed container service, where you hand the cloud one image and it runs copies for you with no cluster to look after. The honest ladder has three rungs. One server while you can. A managed container service when you need copies and updates without an operations team. A cluster when you run many apps, need fine control over how they are placed and networked, or must run the same thing on more than one cloud.
OptionYou look afterGood forWrong for
One server with DockerEverything: restarts, updates, the machineA side project, an internal tool for ten people, the first month of anythingAnything that must stay up when the machine does not
Managed container serviceThe image and a few settingsWeb apps and services that need copies, updates and scaling without a team to run themOdd networking, many apps that must talk privately, running on several clouds
Kubernetes clusterThe deployments, the cluster upgrades, the add-onsMany apps on shared machines, fine control, one way of working across clouds and your own data centreOne small app, a team with nobody to run it, a deadline this week
The three clouds. Each sells a managed cluster where the control plane is run for you: GKE on Google Cloud, EKS on AWS, AKS on Azure. The nodes, the deployments and the upgrades are still yours. Each also sells the simpler managed container service: Cloud Run, Fargate with ECS, and Container Apps. Start there unless you can name the reason not to.

Reading the cluster when something is wrong

In plain English: a cluster rarely tells you “it is broken”. It tells you a pod’s state in one word, and each word points at one cause. Pending means no node had room, or something it needs, such as its storage, is not there yet. ImagePullBackOff means it could not fetch the image: a wrong name, a wrong tag, or no permission. CrashLoopBackOff means the app starts and dies, over and over, and the answer is in its logs. OOMKilled means it used more memory than its limit and was killed. Running but no traffic usually means the readiness check is failing or the service’s label does not match the pod’s.
The order to look
1. kubectl get pods: which word?
2. kubectl describe pod: the events at the bottom say why.
3. kubectl logs: what the app itself said.
4. kubectl rollout undo: if it started with the last change, put it back first and think second.
The two checks that keep it honest
A readiness check asks “may I send you traffic?” and holds traffic back until the answer is yes. A liveness check asks “are you still alive?” and restarts the pod when the answer is no. Get them backwards and a slow start becomes a restart loop.

When someone asks… the short answer

In plain English: each line is a question as a colleague, a client or an interview panel would put it, then the answer that shows you have done it, then why the usual answer falls short.
“What is Kubernetes, in one sentence?” → A manager that runs containers across many computers and keeps the number you asked for running: restarting, replacing, scaling and updating them without a person. Docker makes the boxes; Kubernetes runs the port.
“How is it different from running Docker on a server?” → Docker runs a container on one machine and stops there. Kubernetes places containers across a cluster, restarts them when they die, moves them when a machine fails, scales them with load and rolls out new versions without downtime. Same box, with a port around it.
“Container or virtual machine?” → A container shares the computer’s operating system and packs only the app: megabytes, starts in a second. A virtual machine is a whole pretend computer: gigabytes, starts in minutes. Containers give density and speed; virtual machines give stronger isolation.
“What is a pod?” → The smallest thing the cluster runs: one container, or a few that must share an address and a box. You rarely make pods by hand; a deployment makes and replaces them for you.
“What does a deployment do?” → It is your wish written down: this image, this many copies, updated this way. The cluster keeps reality matching it, and keeps the previous version so you can roll back with one command.
“Why do I need a service if the pods have addresses?” → Pod addresses change every time a pod is replaced. A service is one steady address in front of whichever pods are alive, found by their labels. Callers talk to the service and never learn a pod’s address.
“How does the outside world reach the app?” → Through an ingress: one door into the cluster that holds the certificate and routes by site name and path to the right service. In front of it, a load balancer from the cloud, which spreads traffic across machines, brings the traffic to the nodes.
“How do I deploy a new version?” → Change the image tag in the file and apply it. The cluster replaces copies a few at a time, waiting for each new one to pass its readiness check, so the app never goes fully down. If it goes wrong, rollout undo.
“Where do passwords and settings go?” → Not in the image. Settings go in a config map and passwords in a secret, both handed to the pod when it starts, so one image runs in test and production with different envelopes.
“A pod says CrashLoopBackOff. What first?” → Read its logs. The app is starting and dying; the reason is nearly always in what it printed before it died, such as a missing setting or an unreachable database.
“A pod says Pending for ten minutes.” → Nothing had room for it. Describe the pod and read the events: not enough processor or memory on any node, or a volume that cannot be attached. Add a node or lower the request.
“When should we not use Kubernetes?” → One small app, nobody to run the cluster, or a deadline this week. Use a managed container service that takes one image and runs copies for you. A cluster earns its keep when many apps share it or you need fine control.
“What does the cloud run for us in a managed cluster?” → The control plane: the brain that stores your wishes and decides where pods run. You still own the nodes, the deployments, the upgrades and the add-ons. Managed is not the same as serverless: you still have machines to look after.
“How many nodes do we need?” → Add up what every copy requests, pack it onto nodes, then keep one node’s worth of headroom so a node can fail without pods being thrown off. Fewer, larger nodes waste less; more, smaller nodes lose less when one dies.
Words in these lines. Container: an app packed in a box with everything it needs. Image: the baked copy a container runs from. Cluster: the group of computers Kubernetes manages as one. Node: one computer in it. Pod: the smallest thing the cluster runs. Deployment: your written wish for an image, a number of copies and how to update. Service: one steady address in front of pods. Ingress: the one door from the internet. Control plane: the cluster’s brain. Readiness check: the test before a pod gets traffic. Config map and secret: settings and passwords handed to a pod.
